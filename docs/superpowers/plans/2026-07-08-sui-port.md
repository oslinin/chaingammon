# Sui Port Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Sized for a Sonnet-class worker: read the named reference before writing anything, copy patterns instead of inventing them, and treat SDK specifics as "look up in the linked docs at implementation time" — this plan pins architecture and interfaces, not third-party API signatures.

**Goal:** A self-contained Sui-native Chaingammon at `sui/` on a long-lived `sui` branch: Move packages for agents/matches/ELO, a standalone Next.js app (copied game libs, zero imports from `frontend/`), zkLogin onboarding via Enoki, SUI-staked rated play with on-chain dice, commit-reveal dice for unrated play, and Seal-gated agent weights on Walrus — ending in a Sui Overflow 2026 submission.

**Spec:** `docs/superpowers/specs/2026-07-07-sui-port-design.md` (read it FIRST; the owner decisions block at the top governs scope: standalone app, SUI-only stakes, Enoki hosted, adjudication spec-only, fresh agent population).

**Architecture:** Three small Move modules (`elo`, `agent`, `game_match` — not `match`, a reserved Move keyword) — the rules engine stays off-chain. The app copies the chain-agnostic libs from `frontend/` (rules engine, match engine, Nostr/WebRTC matchmaking, board UI, ONNX eval) and talks to Sui with `@mysten/sui` + `@mysten/dapp-kit` + Enoki directly. Matches settle by co-signed ed25519 session-key signatures verified in Move; stakes are `Balance<SUI>` inside the shared Match object.

**Tech Stack:** Sui Move (2024 edition), `sui` CLI (pinned testnet release), TypeScript/Next.js 16 (webpack), `@mysten/sui`, `@mysten/dapp-kit`, `@mysten/enoki`, Walrus + Seal SDKs, Playwright.

**Project rules to obey (every task):**
1. **All work happens on the `sui` branch** (Task 0 creates it). Never modify `frontend/`, `contracts/`, `server/`, or `agent/` except where a task explicitly says so (Task 7's trainer flag is the only exception).
2. **No commits without owner approval.** Each task ends "show the owner the diff"; no `git commit` steps.
3. **`pnpm` only**; Python via `uv`. Playwright in sandboxes: append `--config playwright.sandbox.config.ts` equivalents — `sui/app` gets its own copy of the sandbox config in Task 4.
4. **`sui/README.md` is the port's manual.** EVERY task updates it so the owner can always install, run, and test the current state from a clean machine. Root `README.md` gets one pointer line (Task 0) and is otherwise untouched.
5. **CHANGELOG.md** — one entry per task under `## [Unreleased]` on the `sui` branch.
6. **Copy manifest:** every file copied from `frontend/` is recorded in `sui/README.md` under "Copied modules" with its source path and the master commit hash it was copied at. This is the hand-port ledger the spec requires.
7. **Third-party SDKs (Enoki, Walrus, Seal, dapp-kit):** consult current docs at implementation time — `https://docs.sui.io`, `https://docs.enoki.mystenlabs.com`, `https://docs.wal.app` (Walrus), Seal docs via `https://seal-docs.wal.app` or the MystenLabs/seal repo. If a doc URL 404s, search the MystenLabs GitHub org. Do NOT trust this plan (or training data) for exact function names.

**Owner prerequisites (flag loudly and skip the dependent steps if missing):**
- Enoki API key + Google OAuth client ID (Task 5) — owner creates at the Enoki portal; worker consumes via `sui/app/.env.local` (`NEXT_PUBLIC_ENOKI_API_KEY`, `NEXT_PUBLIC_GOOGLE_CLIENT_ID`).
- Testnet SUI for the deployer address (Tasks 6–8) — faucet.
- Walrus/Seal testnet availability (Task 7).

## Task 3: `game_match.move` — lifecycle + co-signed settlement

- [ ] **Step 1: Read** spec §4; the EVM result-hash scheme in `frontend/app/play-human/PlayHumanClient.tsx` (~lines 308–386, the `finishGame` encoding) so the Sui result message covers the same fields (players, winner, stakes, match id, nonce-equivalent = the Match object id, which is unforgeable — document that simplification); and `sui::ed25519` docs.
- [ ] **Step 2: Module.** `sources/game_match.move` (named `game_match`, NOT `match` — `match` is a reserved Move keyword, `module chaingammon::match` fails to parse; the `Match` struct name is fine): shared `Match` object with `state: u8` (OPEN/PLAYING/SETTLED/CANCELLED), `creator/joiner: address`, `session_pk_a/b: vector<u8>`, `stake: Balance<SUI>`, `rated: bool`, `created_epoch: u64`. Entry functions: `open(stake_coin, session_pk, rated, ctx)`, `join(match, stake_coin, session_pk, ctx)` (equal stake required), `settle_cosigned(match, winner: address, sig_a, sig_b, ctx)` — rebuild the canonical result bytes in Move (`bcs::to_bytes` of a `ResultMsg` struct containing match id + winner), verify BOTH ed25519 signatures against the registered session pubkeys, pay the pot to the winner, set SETTLED, emit event; `cancel_unjoined(match, ctx)` (creator refund, only while OPEN); `abandon(match, ctx)` — after `ABANDON_EPOCHS` (constant, 7) past join, split the pot 50/50 and mark CANCELLED (the griefing relief valve until adjudication ships).
- [ ] **Step 3: Signature fixtures.** `sui/scripts/gen_fixtures.ts` (`@mysten/sui` keypairs): deterministically derive two ed25519 keypairs from fixed seeds, sign the canonical result bytes for a fixture match, print pubkeys+sigs as Move test constants. Commit the generated constants into `tests/game_match_tests.move` with a comment pointing at the generator.
- [ ] **Step 4: Tests**: full happy path (open→join→settle, winner receives 2×stake), wrong sig aborts, one-sig aborts, unequal stake join aborts, double-settle aborts, cancel_unjoined refunds, abandon splits after epoch advance (test_scenario `next_epoch`). ELO: settle calls `elo` + profile/agent hooks — for v1 wire agent ELO only when the match records agent ids (add `Option<ID>` agent refs to Match; human ELO lands with profiles in Task 5). `sui move test` green.
- [ ] **Step 5: README** (lifecycle diagram in ASCII, CLI walkthrough on localnet). **CHANGELOG**. Show the owner the diff.

## Task 6: Rated play — stakes + on-chain dice

- [ ] **Step 1: Wire open/join.** "Play rated (stake X SUI)" flow: creator calls `match::open` (session pubkey = fresh ed25519 keypair generated in-browser, held in memory exactly like the EVM session key — read the `sessionAccount` pattern in `PlayHumanClient`), match id doubles as the Nostr match id; joiner calls `join`. Both stakes locked on-chain before the first move.
- [ ] **Step 2: On-chain dice.** Add `match::roll(match, r: &Random, ctx)` in Move (reads `sui::random`, derives d1,d2, emits `DiceRolled{turn_index, d1, d2}`, enforces alternating roller + monotonic turn_index — this is the anti-grinding property, note it in a comment). Client: on your turn, submit the PTB (sponsored when Enoki, plain otherwise), then both clients consume the event via `subscribeEvent`/polling. Read the `sui::random` docs for the entry-function pattern (Random is a shared object at 0x8; randomness calls have PTB restrictions — follow the documented pattern exactly).
- [ ] **Step 3: Settle.** On game over, both session keys sign the canonical result bytes (must byte-match Move's `bcs::to_bytes` — generate them with the same `@mysten/sui` bcs schema; reuse the Task 3 fixture generator as the reference), winner (or either side) submits `settle_cosigned`. Render pot payout + new ELO.
- [ ] **Step 4: E2E** on localnet: full rated match with model moves — stakes locked, dice from chain events, settle pays winner, ELO changes on both profiles. This is the plan's hardest test; budget for it (reuse the Task 5 globalSetup localnet).

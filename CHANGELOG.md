- **`sui/app` — standalone unrated P2P play** (`sui` branch, Task 4 of `docs/superpowers/plans/2026-07-08-sui-port.md`). A new Next.js 16 app, entirely separate from `frontend/` (no shared code, no chain dependency at all — proves the copied game core stands on its own before any Sui wiring lands in Tasks 5-6). Copied by hand from `frontend/` at commit `7519bd5` (see `sui/README.md`'s "Copied modules" table): the rules engine, match engine, gnubg position/match-id encoding, ONNX move evaluator + worker, Nostr matchmaking/presence client, the ELO-biased pairing algorithm, the WebRTC transport, and the `Board`/`DiceRoll` UI. Deliberately dropped rather than copied: the 6 image-skin board themes (~166MB of pre-rendered board/checker art — kept only the 19 flat-color CSS themes, which need no image assets), the doubling cube, ENS/wallet/session-key auth, and on-chain settlement (Task 6 wires rated play + settlement back in). New `sui/app/lib/commit_reveal_dice.ts` replaces `frontend/lib/drand_dice.ts`'s drand-beacon dice with a peer-only scheme: each turn both players generate a secret, exchange `{type:"dice-commit", h:keccak256(secret)}` then (only after both commitments are in) `{type:"dice-reveal", secret}`, and derive `dice = keccak256(secret_side0 ‖ secret_side1 ‖ turnIndexBE8) mod 36` — the same mod-36→(d1,d2) mapping as the drand path, so neither peer can bias a roll and no external network call is needed at all (matchmaking's Nostr relays are the only network dependency). `sui/app/app/play/page.tsx` is a from-scratch trim of `PlayHumanClient.tsx`: hello handshake assigns sides by comparing ephemeral Nostr pubkeys (lower pubkey = side 0), then the commit-reveal round runs symmetrically for both peers every turn regardless of whose move it is. Same testMode window hooks as the original (`__HVH_TEST_MODE`, `__HVH_GAME_STATE`, `__HVH_MY_SIDE`, `__HVH_MODEL_MOVES`, `__HVH_MODEL_MOVE_COUNT`, `__HVH_MATCH_LENGTH`) so the Playwright harness is a near-identical fork. `sui/app/tests/unrated_hvh.spec.ts` (adapted `hvh_test_utils.ts` — same WebRTC/bridge/in-memory-Nostr-relay mocks, no wallet mock needed since there's no wallet, no drand mock needed since dice never touch the network) plays a full model-moves game across two mocked browser contexts and asserts both peers resolve to the identical winner/score/`position_id` with the winner having borne off all 15 checkers — CI-verified (both locally via `playwright.sandbox.config.ts` and in `.github/workflows/sui-ci.yml`'s new `app` job with real Playwright-managed browsers). `sui/app/tests/commit_reveal_dice.spec.ts` unit-tests the dice derivation and the mismatched-reveal abort path directly. Caught and fixed two real bugs while getting the E2E game to resolve: the `hello` handshake was only sent from inside a `peer.onState("open")` callback, but the connection is already "open" by the time `/play` mounts (that's what triggered the navigation there), and `onState` doesn't replay a state that already happened — so `hello` never sent, sides never assigned, game never started; fixed by also sending immediately on mount (idempotent — `peer.send` no-ops until the channel is open, and the receiver ignores a duplicate `hello`). And: the peer who just moved starts the next turn's commit-reveal dice round synchronously, but the other peer only starts it after asynchronously processing that move message, so a `dice-commit` for the next turn could arrive and be silently dropped before the receiving side had locally started its own round for that turn — deadlocking the game partway through; fixed with a small out-of-order buffer (`pendingDiceMsgsRef`) drained when the local round starts.
- **`chaingammon::game_match` Move module** (`sui` branch, Task 3 of `docs/superpowers/plans/2026-07-08-sui-port.md`; module named `game_match`, not `match` — `match` is a reserved Move keyword (a native pattern-matching expression), so `module chaingammon::match` fails to parse; CI's first run on this task caught exactly that, before any real logic was even type-checked — the `Match` struct name itself is unaffected) — the match lifecycle (`OPEN -> PLAYING -> SETTLED`, with `CANCELLED` reachable from either via `cancel_unjoined`/`abandon`) and co-signed settlement, replacing the on-chain half of `MatchRegistry.settleWithSessionKeys` and the `finishGame`/`settleMatch` flow in `frontend/app/play-human/PlayHumanClient.tsx`. `open`/`join` lock equal SUI stakes and register each side's session pubkey; `settle_cosigned` rebuilds the canonical result bytes on-chain (a `ResultMsg` of domain string + an app-level `app_match_id` + winner, BCS-encoded) and requires BOTH session keys' ed25519 signatures over it before paying the full pot to the winner — the caller supplies only signatures, never the message, so nobody can claim an unsigned result. Deliberately binds an app-supplied `app_match_id` (the off-chain Nostr/WebRTC match id) rather than Sui's own object id, so the anti-replay property (a Match can only ever settle once) doesn't depend on how the runtime assigns object ids — same guarantee, less coupling, and it makes offline-generated signatures reproducible. `settle_cosigned_with_agents` is the same path plus updating both sides' ELO via `chaingammon::elo`/`agent::record_result`, gated on the match having recorded both agents' ids. `cancel_unjoined` (creator, OPEN-only, no timeout) and `abandon` (permissionless 50/50 split after `ABANDON_EPOCHS = 7`) are the v1 griefing relief valves — the spec's Nautilus adjudication path stays design-only per the owner's decision. `sui/scripts/gen_fixtures.ts` derives two real Ed25519 keypairs (via `@mysten/sui`) and actually signs the exact on-chain message bytes, rather than hand-deriving test fixtures; the 10 tests in `game_match_tests.move` embed that real output and cover the happy path (winner receives 2x stake), independently-wrong sig_a and sig_b, double-settle, unequal-stake and self-join aborts, the cancel/abandon refund paths (`test_scenario::next_epoch` for the timeout), and the agent-ELO settlement. - **`MatchRegistry.settleWithSessionKeysAndSplit`** — trustless session-key settlement WITH on-chain payout via `MatchEscrow.payoutSplit`, closing phase **Team-5** of `docs/team-mode.md`. Same auth message as `settleWithSessionKeys` ("Chaingammon:open" — the session key is authorized at game open before the split is known, so a single human auth signature works for both paths). Single-winner solo and N-way team splits both go through the same path (`payoutSplit` handles N=1 as the degenerate case). New `NoEscrowConfigured` error fires when `recordMatchAndSplit` is called before the wiring. `contracts/script/deploy.js` now calls `registry.setMatchEscrow(escrowAddr)` after deploying both contracts, so a fresh deploy is wired end-to-end. - **`MatchEscrow.payoutSplit(matchId, winners[], shares[])`** — settler-only multi-recipient settlement function for team-mode payouts (see `docs/team-mode.md`). Aligned arrays: `shares[i]` is the wei sent to `winners[i]`. Sum of shares MUST equal the pot (settler pre-computes the split; contract verifies it). Recipients are NOT restricted to the two depositors — team-mode design assumes one address per side stakes (per-match terms can change every match — there is no team treasury) and the team's internal split is decided off-chain, then committed at game-end by `MatchRegistry`. Effects-then-interactions: `settled` flag flipped before any of the N transfers, so reentrant calls hit `AlreadySettled`. Zero-share entries are allowed (settler may want to record team membership without paying) and skipped at transfer time. Zero-address winners revert. New errors: `EmptyWinners`, `LengthMismatch`, `ZeroAddressWinner`, `ShareSumMismatch`. Reuses the existing `PaidOut(matchId, winner, amount)` event (one per non-zero share). 16 new Hardhat tests cover 50/50 split, 3-way custom split summing to pot, non-depositor winners (the team-mode case), zero-share skip, all four new error reverts plus length/match-not-open/already-settled/cross-payout-blocking/no-settler. Lands phase **Team-3** of `docs/team-mode.md`.

### Fixed

- **`rules_engine.ts` generated moves that its own validator rejected — HvH games could stall unrecoverably.** Two bugs: (1) `parseMove` did not understand the gnubg `(n)` repeat suffix that `generateLegalMoves` emits for doubles (`"9/4(2) 7/2 4/off"`), silently dropping the repeat so `isLegal` simulated only one copy and rejected the move; (2) the compact grouping collapsed repeated sub-moves onto their first occurrence's position, synthesising orderings that were never played (e.g. `"9/8(2) 10/9"` when the second 9/8 is only possible after 10/9 vacates the point). When every candidate for a turn was affected, the auto-play (and any move applier) had no committable move and the game hung. `parseMove` now expands `(n)` repeats (first copy carries the hit flag), and `generateLegalMoves` keeps the compact form only when it still validates, falling back to the actual played order expanded. A 300-game random-play fuzz (516k generated moves) passes with zero generator/validator disagreements (was ~0.6% rejected).
- **Home Play/Play($) buttons unusable in Playwright testMode** — the Privy-authentication gate added to the home page ignored `__HVH_TEST_MODE`, so E2E matchmaking could never start. The home page now mirrors `PlayHumanClient`'s testMode fallback: the flag (read in an effect to keep hydration clean) bypasses the Privy check and takes the address from the test's mock wallet.
- **Sepolia default RPC in `contracts/hardhat.config.js`** — was `https://rpc.sepolia.org` (Cloudflare 522 by late 2025); now `https://ethereum-sepolia.publicnode.com`. Documents `SEPOLIA_RPC_URL` in `contracts/.env.example`.

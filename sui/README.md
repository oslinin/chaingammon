# Chaingammon on Sui

A self-contained, Sui-native variant of Chaingammon: Move packages for agent
objects, matches, and ELO; a standalone Next.js app with its own copy of the
chain-agnostic game core (rules engine, matchmaking, board UI); zkLogin
onboarding; SUI-staked rated play with on-chain dice; and Seal-gated agent
weights on Walrus.

- **Design spec:** [`docs/superpowers/specs/2026-07-07-sui-port-design.md`](../docs/superpowers/specs/2026-07-07-sui-port-design.md)
- **Implementation plan:** [`docs/superpowers/plans/2026-07-08-sui-port.md`](../docs/superpowers/plans/2026-07-08-sui-port.md)
- **Branch:** `sui` (long-lived; rebased onto `master` periodically). This directory does not exist on `master`.
- **Relationship to the main app (`frontend/`):** intentionally separate. No shared code, no shared contracts. See "Copied modules" below for what was ported by hand from `frontend/` and when.

This README is kept current after every task in the implementation plan — it should always be enough to install, build, and test whatever has landed so far from a clean machine.

Task 4 adds `sui/app` — a standalone Next.js app proving the copied game core plays a full unrated peer-to-peer game with NO chain dependency at all: two browsers matchmake over Nostr, exchange commit-reveal dice, and play to a winner. See "Using the app" below.

Task 5 adds `chaingammon::profile` (`HumanProfile` + a shared `ProfileRegistry`, mirroring `agent.move`'s ELO/match-count shape but as a *shared* object so either player can settle a match touching both sides' profiles) and `game_match::settle_cosigned_with_profiles`, plus a mock sign-in flow in `sui/app` (no Enoki API key / Google OAuth client id configured in this environment — see "Sign-in and human profiles" below). This is the first point `sui/app` actually talks to the Move package: `sui/scripts/publish_localnet.ts` publishes it to a real local network and a dedicated Playwright spec (`tests/profile_signin.spec.ts`, CI job `app-localnet`) signs in and asserts the resulting HumanProfile's ELO renders — CI-confirmed end to end, including a full localnet boot + publish inside the CI job itself. Getting there took four real bugs, in order: (1) Move has no first-class tuple values — `let ids = (a, b)` doesn't compile, only the transient `let (a, b) = expr` destructuring form does; (2) `sui::transfer::share_object` is restricted to a type's *declaring* module, so a test-only constructor in a different test module couldn't share what it built — fixed by sharing inside `profile.move` itself and returning only the id; (3) a composite GitHub Action's own `action.yml` cannot reference `secrets.*` (the Actions template processor eagerly evaluates any literal `${{ }}` in the file, including inside a prose description string, and `secrets` isn't in scope there); (4) `sui move build --dump-bytecode-as-base64`'s JSON output gets corrupted by an interactive "no config found, create one?" prompt on a machine with no `~/.sui/sui_config/client.yaml` yet (any fresh CI runner) — fixed by triggering that one-time config creation on a throwaway earlier call.

The E2E game exposed two real bugs during Task 4 development, both fixed before this landed (worth recording since they're exactly the class of bug a chain-agnostic P2P transport invites): (1) the `/play` page only sent its `hello` handshake message from inside a `peer.onState("open")` callback, but by the time a player navigates there matchmaking has *already* observed "open" (that's what triggered the navigation) — `onState` is a plain setter, not a replay of current state, so the callback's "open" branch would then wait for a state transition that had already happened and would never happen again, and `hello` was never sent. Fixed by also calling `sendHello()` unconditionally right after registering the callback (harmless double-call — `peer.send` no-ops until the channel is open, and the receiver ignores a duplicate `hello` once a side is already assigned). (2) the commit-reveal dice round for turn N+1: the peer who just moved starts it synchronously, but the other peer only starts it after asynchronously processing that move message, so a `dice-commit` for N+1 could arrive before the receiving side had locally called `startDiceRound(N+1)` — and was silently dropped, deadlocking the game. Fixed with `pendingDiceMsgsRef`, a small out-of-order buffer drained by `startDiceRound` when it runs.

Task 6 adds rated play: real SUI stakes locked via `game_match::open`/`join`, dice sourced from `sui::random` on-chain (`game_match::roll`, gated to the alternating roller by `turn_index` parity so a player can never see a roll before it lands and never retry to reroll — the anti-grinding property the EVM version never had), and cosigned settlement (`settle_cosigned_with_profiles`) that pays the winner and updates both `HumanProfile`s' ELO. App-side: a new `sui/app/app/play-rated/page.tsx` (`lib/rated_match_client.ts` wraps the on-chain calls) and a second "Play rated (0.1 SUI)" button on the home page, matchmaking through a separate Nostr presence pool so a rated searcher never pairs with an unrated one (`PresenceContent` gained an optional `rated` flag — `lib/nostr.ts`). The roller reads d1/d2 straight from its own transaction's `DiceRolled` event; the other side independently polls `queryEvents` for the same `turn_index` rather than trusting a WebRTC-relayed value — trusting the peer there would defeat the entire reason for on-chain dice. See "Rated play" below for the full walkthrough and `tests/rated_hvh.spec.ts` for the end-to-end proof (stakes locked, dice from chain events, settle pays the winner, ELO moves on both profiles) — CI-confirmed green on commit `b3acbb1`, after three real bugs: (1) the home page's two "Play unrated"/"Play rated" buttons made `hvh_test_utils.ts`'s old `getByRole("button", {name:"Play"})` locator ambiguous (Playwright's default name match is substring, not exact) — narrowed to the full label; (2) `play-rated/page.tsx`'s `HelloMsg` never carried a `profileId`, so `oppProfileIdRef` stayed `null` forever and settlement silently fell back to the no-ELO `settle_cosigned` path every time — the first full CI run got the entire match all the way through a correct on-chain settlement and only failed on the ELO assertion, which is what surfaced it; fixed by adding `profileId` to the hello handshake; (3) `sui start --with-faucet --force-regenesis`'s own genesis/faucet bootstrap turned out to be genuinely non-deterministic in CI — identical setup code (the `-y`-flag fix below) passed on one push and hit the exact same "Wallet Error: No address found with sufficient coins" on the very next push with no code change in between — fixed by retrying the whole spawn-and-wait sequence up to 3 times in `localnet_global_setup.ts`, failing fast the moment the log shows that known-fatal string instead of waiting out the full timeout.

## Sign-in and human profiles (Task 5)

`sui/app` supports two auth modes via `NEXT_PUBLIC_AUTH_MODE` (`sui/app/lib/mock_identity.ts`):

- **`mock`** (the default, and the only mode this environment can run): a real Sui `Ed25519Keypair` generated in the browser and persisted in `localStorage` — a stand-in for zkLogin's real address without the OAuth round-trip. Click "Sign in" on the home page.
- **`enoki`**: real zkLogin (Google) via Enoki + sponsored transactions, per the design spec §6. **Not configured in this environment** — it needs the env vars below in `sui/app/.env.local`. `sui/app/lib/mock_identity.ts::enokiConfigured()` reports whether both are present; the app falls back to `mock` until they are, per the plan's "do NOT stall the plan" instruction for this step. Wiring the real Enoki SDK calls is a follow-up once the owner has provisioned those keys.

| Env var | Required for | Where to get it |
|---|---|---|
| `NEXT_PUBLIC_AUTH_MODE` | Selecting `mock` (default) vs `enoki` | N/A — set to `enoki` once both vars below are set |
| `NEXT_PUBLIC_ENOKI_API_KEY` | `enoki` mode | [Enoki portal](https://portal.enoki.mystenlabs.com/) — create a project, add a Google OAuth provider |

On sign-in (`mock` mode), the app:
1. Loads or generates the persisted keypair.
2. Loads `/localnet-config.json` (see below) — if absent, shows the address only, with a "localnet not configured" note, rather than stalling.
3. Requests SUI from the localnet faucet (best-effort).
4. Creates a `HumanProfile` via `chaingammon::profile::create_profile` if the address doesn't have one yet (`profile::has_profile`, a read-only `devInspectTransactionBlock` call — no gas, no signature), then renders its display name and ELO.

## Rated play (Task 6)

Real SUI stakes, on-chain dice, cosigned settlement — the same matchmaking flow as unrated play, but backed by a real `chaingammon::game_match::Match` object instead of nothing.

1. Home page: click **"Play rated (0.1 SUI)"** instead of "Play unrated". Rated searchers matchmake in a separate Nostr presence pool (`PresenceContent.rated`), so you'll only ever pair with another rated searcher.
2. On match, both sides land on `/play-rated?id=…`. A player who hasn't visited "Sign in" first still gets funded (best-effort localnet faucet request) and gets a `HumanProfile` created automatically — rated play always tracks ELO, unlike unrated play where a profile is optional.
3. Side 0 (creator, by the same lower-Nostr-pubkey-wins rule as unrated) calls `game_match::open` with a fresh in-browser session `Ed25519Keypair` (held in memory only, exactly like the EVM `sessionAccount` pattern in `frontend/app/play-human/PlayHumanClient.tsx`) and a 0.1 SUI stake; side 1 (joiner) calls `join` with a matching stake once it learns the new Match's object id over the WebRTC channel.
4. Every turn, the app calls `game_match::roll(match, &Random)` instead of running commit-reveal — but only the side whose turn it is per `turn_index` parity (even → creator, odd → joiner; Move aborts `EWrongRoller` otherwise). That side reads d1/d2 straight from its own transaction's `DiceRolled` event; the other side independently polls `queryEvents` for the same `match_uid`/`turn_index` rather than trusting a WebRTC-relayed value — trusting the peer there would defeat the entire point of on-chain dice.
5. On game over, both session keys sign the same canonical result bytes `game_match.move` reconstructs (`bcs::to_bytes` of `{domain: "Chaingammon:result-sui-hvh", app_match_id, winner}` — see `lib/rated_match_client.ts::canonicalResultBytes`, byte-identical to `sui/scripts/gen_fixtures.ts`'s schema) and exchange signatures over WebRTC. Once both sigs are in, either side submits `settle_cosigned_with_profiles` (falls back to plain `settle_cosigned` if either side's profile id is somehow unknown) — the pot pays the winner and both `HumanProfile`s' ELO update. A double-settle race (both sides submit) is expected and harmless: the second call aborts on `EWrongState`, and the app treats that as "already settled."

```bash
cd sui/app
pnpm exec playwright test --config playwright.localnet.config.ts   # runs rated_hvh.spec.ts too, see below
```

`tests/rated_hvh.spec.ts` (Task 6 Step 4 — "the plan's hardest test") plays one full rated match end to end with model moves on a real local network via the same `globalSetup`/`globalTeardown` as `profile_signin.spec.ts`, then checks TWO independent oracles: the P2P game state (both peers agree on winner/score/`position_id`, same as `unrated_hvh.spec.ts`) and the chain itself — the `Match` object reaches `STATE_SETTLED` with `turn_index > 0` (dice really came from `roll`, not a stub), and both `HumanProfile`s' ELO actually moved (winner's up, loser's down from the fresh-profile default of 1500). **CI-confirmed green on commit `b3acbb1`** — see the Task 6 paragraph in "Status" above for the three real bugs found getting here (button-locator ambiguity, a missing profile-id exchange that silently skipped ELO updates, and a genuinely flaky `sui start` genesis/faucet boot race fixed with a retry loop).

## Encrypted agent weights (Task 7)

Seal-gated, Walrus-stored agent weights — an ERC-7857-style "the NFT owner and only the owner can decrypt the model" story, but enforced by an on-chain Move policy instead of a centralized re-encryption service.

⚠️ **This task is only partially verified.** This sandbox's egress policy blocks `docs.wal.app`, `seal-docs.wal.app`, and `github.com` (confirmed via the proxy's own diagnostics — see `/root/.ccr/README.md`'s "403/407 from the proxy" section — not a real site outage), so the current *verified* Seal testnet key server object ids could not be looked up, and neither a real Seal key server nor a real Walrus publisher/aggregator has ever actually been reached from this environment. Per the plan's own Task 7 Step 2 escape hatch ("if Seal's testnet key servers are unavailable, deliver the Move policy + a skipped-with-reason demo script and flag it"): the Move policy is delivered and CI-verified (`sui move test`, no network needed); the TS/Python scripts are written against the real `@mysten/seal` SDK's shipped type definitions (`node_modules/.pnpm/@mysten+seal@.../dist/*.d.mts` — read directly, the same verification method used for `@mysten/sui` elsewhere in this repo) and typecheck cleanly, but have never been run against a live network. The app's "play vs agent" ONNX-loading UI (Step 4's last bullet) is **not implemented** — it depends on having a real decrypted model to load, which requires the blocked network path.

**`chaingammon::agent::seal_approve`** (`sources/agent.move`) is the on-chain policy: gates decryption of an Agent's weights blob on CURRENT ownership of that specific Agent. Per Seal's `seal_approve*` convention, the first argument is the requested identity with the package-id prefix already stripped by the key server; the function is side-effect-free (`&Agent`, never `&mut`) and denies by aborting (there is no "return false" — "approved" simply means "did not abort"). The identity is the agent's own object id (`id == object::id_to_bytes(agent)`), so owning one Agent can never unlock a *different* Agent's weights. 3 new `agent_tests.move` tests exercise this directly (same `public(package) entry` pattern as `game_match::roll`, so a test module in the same package can call it without a real key server) — 10 Agent tests, 49 Move tests total. CI-confirmed green.

**Upload path**:
- `agent/walrus_upload.py` — sibling of `og_storage_upload.py`, but talks to Walrus's public HTTP publisher/aggregator directly (`PUT $PUBLISHER/v1/blobs?epochs=N`, `GET $AGGREGATOR/v1/blobs/<blobId>`) rather than shelling out to a Node bridge — the public testnet publisher needs no wallet on this side. `sample_trainer.py --upload-to-walrus` (the plan's "THE one permitted edit outside `sui/`") is an alternative to `--upload-to-0g` for trainer checkpoints, same AES-256-GCM-then-upload flow, writing `<ckpt>.walrus.key` instead of `<ckpt>.key`. 13 unit tests mock `httpx.put`/`httpx.get` and pass (`cd agent && uv run pytest tests/test_walrus_upload.py -v`) — no live network needed for these, only response-shape/error-handling logic.
- `sui/scripts/mint_agent.ts` — mints an `Agent`, Seal-encrypts an ONNX export under the agent's own object id (`SealClient.encrypt`), uploads the ciphertext to Walrus, and calls `agent::set_weights(blob_id, content_hash)`. Order matters: since the Seal identity IS the agent's on-chain object id, minting must happen *first* to get that id — the plan's phrasing ("Seal-encrypt an ONNX export, upload to Walrus, agent::mint + set_weights") describes the feature, not this script's literal step order. `content_hash` is a SHA-256 of the *plaintext* ONNX bytes (so `fetch_weights.ts` can verify integrity after decrypting); `blob_id` is stored as the UTF-8 bytes of Walrus's blobId string (base64url text, not raw bytes — storing the string form avoids any base64 alphabet/padding assumptions).
- `sui/scripts/fetch_weights.ts` — fetches the blob ref off-chain, downloads the ciphertext from Walrus, builds a PTB calling `seal_approve`, creates a `SessionKey`, and decrypts. `--demo-denial <agent-object-id>` proves the "non-owner denied" half of Step 5's required proof: it generates a throwaway keypair, attempts the same decrypt flow, and expects `seal_approve`'s owner check to abort — the key servers should refuse to release key shares and `SealClient.decrypt()` should reject.

Both scripts require `SEAL_KEY_SERVER_OBJECT_IDS` (comma-separated) as an env var — **deliberately not hardcoded** here. A web search surfaced object-id-shaped strings for "verified testnet key servers," but they decoded to 33 bytes (not the 32 bytes a real Sui object id must be), which is a strong signal of search-summary hallucination rather than a real address; shipping a plausible-looking-but-wrong default seemed worse than requiring the caller to look the current list up themselves (Seal docs' "Verified Key Servers" page) once this repo is running somewhere with network access.

`sui/scripts/typecheck` (via `pnpm --filter sui-scripts typecheck`) passes for both new scripts, including confirming — without any type cast — that `SuiJsonRpcClient` (`@mysten/sui/jsonRpc`) structurally satisfies `@mysten/seal`'s `SealCompatibleClient`/`ClientWithCoreApi` interfaces, so no separate gRPC client or `.$extend()` dance is needed to use `SealClient`/`SessionKey`/`Transaction.build()` alongside the rest of this repo's `SuiJsonRpcClient`-based scripts.

### Match lifecycle

```
                 open()                    join()
   (nobody) ─────────────────▶ OPEN ─────────────────▶ PLAYING
                                  │                         │
                     cancel_unjoined()          settle_cosigned()
                     (creator, anytime)          (both session sigs)
                                  │                         │
                                  ▼                         ▼
                             CANCELLED                  SETTLED
                                                             ▲
                                                             │
                                                        abandon()
                                                (anyone, ABANDON_EPOCHS
                                                 after join, 50/50 split)
                                                             │
                                                             ▼
                                                        CANCELLED
```

Off-chain play (WebRTC + the client rules engine) happens entirely between `join` and `settle_cosigned` — this module never sees individual moves, only the final signed result. There is no ADJUDICATING state in v1; `abandon` is the interim relief valve for a non-cooperating opponent (see the design spec §7 for the deferred Nautilus adjudication path).

## CI

`.github/workflows/sui-ci.yml` runs on every push/PR to the `sui` branch, with three independent jobs:
- `move` — installs the `sui` CLI and runs `sui move build` + `sui move test`.
- `app` (added Task 4) — `pnpm install`, `tsc --noEmit`, `next build`, installs real Playwright browsers (`playwright install --with-deps`), then `pnpm run test:e2e` (the chain-agnostic unrated-play suite; `profile_signin.spec.ts` self-skips here since this job has no `sui` CLI).
- `app-localnet` (added Task 5) — installs the `sui` CLI too, then `pnpm run test:e2e:localnet` (`playwright.localnet.config.ts`, which now runs both `profile_signin.spec.ts` and `tests/rated_hvh.spec.ts` — Task 6 — against a real local network; see "Sign-in and human profiles" and "Rated play" above). Kept as its own job so a slow/flaky localnet never blocks the unrated-play suite's own signal.

The CLI install step is factored into `.github/actions/install-sui-cli` (a composite action), shared by all three localnet-backed steps (the `move` job, plus `app-localnet` for both Task 5 and Task 6's specs).

Kept separate from the main repo's `ci.yml` so Sui-branch work never conflicts with `master` CI.
